# CI の失敗を解消する

プルリクエストの失敗している CI チェックを診断し、修正してプッシュする。
全チェックが成功するか、リトライ上限に達するまでループする。
各ラウンドでの承認は求めず修正を適用し、最終的なサマリーのみレビューを受ける。

## ワークフロー

### Step 1：PR とリポジトリを決定する

`responding-to-pr-review` と同じ検出方法を使う：

- **PR の URL が与えられた場合**：URL から `OWNER/REPO` と `PR_NUMBER` をパースする。
- **`OWNER/REPO` と `PR_NUMBER` が明示された場合**：そのまま使用する。
- **それ以外**：自動検出する：

  ```bash
  gh repo view --json nameWithOwner --jq .nameWithOwner  # OWNER/REPO
  gh pr view --json number --jq .number                  # PR_NUMBER
  ```

  `gh pr view` が失敗した場合は、PR の URL または番号をユーザーに確認する。

### Step 2：チェックの完了を待つ

```bash
gh pr checks <PR_NUMBER> -R <OWNER/REPO> --watch
```

### Step 3：失敗しているチェックを列挙し、ログを取得する

```bash
gh pr checks <PR_NUMBER> -R <OWNER/REPO> --json name,bucket,link
```

`bucket` が `fail` の各チェックについて、`link` から run ID を取り出し、
失敗した部分のログのみを取得する：

```bash
gh run view <run-id> --log-failed
```

### Step 4：ログを分析し、失敗を分類する

Step 3 で取得した各失敗ログをまず読む。ログを分析する前にブランチの
チェックアウトやローカルでの再現に飛びつかない。各失敗を次の3種類に分類する：

1. **一時的な問題に見える** — ネットワークの瞬断、インフラのタイムアウト、
   レート制限、この PR の diff とロジック的に無関係な flaky テスト、
   "connection reset" など → Step 5（リラン）で扱う。チェックアウトは不要。
2. **ログだけで根本原因が明確** — file:line とメッセージが明示された
   lint/型/ビルドエラー、CI 固有の設定で説明がつく secrets/環境変数/権限の
   不足など → 修正内容をログから直接組み立てる。ログがすでに示している
   内容をローカルで確認するためだけに時間をかけない。
3. **判断がつかない** — ログだけでは根本原因、または修正案が実際に効くか
   どうかが分からない → Step 7 のローカル再現対象としてマークする。ブランチ
   のチェックアウトが必要になるのはこのバケットだけ。バケット1・2では
   チェックアウトしない。

チェックを `.github/workflows/*.yml` 内のジョブに対応付けられない場合、
またはローカル再現が届かないもの（CI からしかアクセスできない外部サービス
に依存するなど）に依存する場合は、バケットによらず診断不能と判断する。
このチェックをスキップして保留リストに追加し、残りの処理を続ける。

### Step 5：一時的な失敗をリランする

Step 4 で一時的と分類した失敗については、コードには触れずそのジョブだけを
リランする：

```bash
gh run rerun <run-id> --failed
```

同じチェックが複数ラウンドにわたって一時的と分類され続ける場合
（Step 9 のラウンド数を参照）、それ以上は一時的な問題として扱わず、保留
リストに移して flaky として報告する。無限にリランし続けない。

### Step 6：必要な場合のみ PR のブランチをチェックアウトする

今回のラウンドの失敗がすべて一時的（Step 5 のみで、再現もコミットも不要）
なら、このステップ全体をスキップする。それ以外の場合、ローカル再現
（Step 7）や修正のコミット（Step 8）を行う前に、現在の作業ツリーを PR の
ブランチに切り替える。この目的で git worktree は作らない：

```bash
gh pr checkout <PR_NUMBER> -R <OWNER/REPO>
```

まず `git status` を確認する：

- **作業ツリーがクリーン** → そのまま `gh pr checkout` を実行する。
- **未コミットの変更がある**（無関係な作業中のもの） → 自己判断で stash・破棄・
  worktree の作成をしない。作業を続ける前に、どう進めるか（stash して後で戻す、
  先にコミットする、このケースに限り worktree を使う、など）をユーザーに確認する。

同じループ内の前のラウンドですでに PR のブランチにいる場合は、再度
チェックアウトする必要はない。`git status` が離れた時点のままであることだけ
確認する。

### Step 7：判断がつかない失敗をローカルで再現する

Step 4 で判断がつかないとマークした各失敗について：

- 失敗したチェック名を `.github/workflows/*.yml` 内のジョブに対応付け、
  失敗ログに表示されるステップ名・順序を手がかりに、該当ステップの
  `run:` コマンド（または `uses:` アクション）を特定する。
- そのコマンドをローカルでそのまま実行する。
- **ローカルで再現した** → 実際のコード/ロジックのバグと判断する。修正し、
  同じコマンドを再実行してパスすることを確認してから次に進む。
- **ローカルで再現しない**（自分の環境では成功する） → CI 環境固有の問題と
  判断する。ログの内容から直接修正する。再現できない環境差分に対して
  ローカルで延々と試行を繰り返さない。
- **該当ステップ・コマンドを特定できない、またはローカルで実行できない**
  （CI からしかアクセスできない外部サービスに依存するなど） → 診断不能と
  判断し、このチェックをスキップして保留リストに追加し、残りの処理を続ける。

### Step 8：グループ化してコミットする

Step 4 のバケット2と Step 7 で再現・修正した失敗のうち、同一の根本原因に
起因するもの（例：複数ファイルで同じ lint ルール違反）は1つの論理的な修正
としてグループ化する。グループごとに1コミットとして適用する。各ラウンドで
のユーザー承認は不要：

```bash
git add <changed files>
git commit -m "<修正内容>"
git push
```

Step 5 のリランはコミット不要（すでにトリガー済み）。

### Step 9：全チェック成功か上限に達するまでループする

Step 5 のリランをトリガーし、Step 8 の修正をプッシュしたら、Step 2 に戻り
再度チェックの完了を待つ。

- **全チェックが成功した** → Step 10 に進む。
- **再チェックを5ラウンド行っても全チェックが成功しない** → 停止して報告する。
- **今回のラウンドで修正可能な失敗もリランも1件もなかった**（すべて診断不能
  だった） → それ以上ループしても進展しないため早期に停止する。

### Step 10：結果を報告する

以下を1行ずつ列挙する：

- リラン：チェック名と、リランの根拠にした一時的な問題の兆候
- 適用した修正：コミットハッシュ、チェック名、修正内容
- スキップしたチェック：チェック名とその理由（診断不能、flaky、外部サービスなど）

## 備考

- 失敗を通すためだけの抑制（テストの無効化、lint-ignore コメント、ステップのスキップなど）は
  行わない。根本原因を修正すること。本当に抑制が妥当と思われる場合は、実行せずに
  ユーザーに確認する。
- `gh` CLI（`gh auth login`）が必要。
