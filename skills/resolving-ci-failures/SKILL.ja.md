# CI の失敗を解消する

プルリクエストの失敗している CI チェックを診断し、修正してプッシュする。
全チェックが成功するか、リトライ上限に達するまでループする。
各ラウンドでの承認は求めず修正を適用し、最終的なサマリーのみレビューを受ける。

## ワークフロー

### Step 1：PR とリポジトリを決定する

`responding-to-pr-review` と同じ検出方法を使う：

- **PR の URL が与えられた場合**：URL から `OWNER/REPO` と `PR_NUMBER` をパースする。
- **`OWNER/REPO` と `PR_NUMBER` が明示された場合**：そのまま使用する。
- **それ以外**：自動検出する：

  ```bash
  gh repo view --json nameWithOwner --jq .nameWithOwner  # OWNER/REPO
  gh pr view --json number --jq .number                  # PR_NUMBER
  ```

  `gh pr view` が失敗した場合は、PR の URL または番号をユーザーに確認する。

### Step 2：PR のブランチをチェックアウトする

現在の作業ツリーを PR のブランチに切り替える。この目的で git worktree は作らない：

```bash
gh pr checkout <PR_NUMBER> -R <OWNER/REPO>
```

まず `git status` を確認する：

- **作業ツリーがクリーン** → そのまま `gh pr checkout` を実行する。
- **未コミットの変更がある**（無関係な作業中のもの） → 自己判断で stash・破棄・
  worktree の作成をしない。作業を続ける前に、どう進めるか（stash して後で戻す、
  先にコミットする、このケースに限り worktree を使う、など）をユーザーに確認する。

### Step 3：チェックの完了を待つ

```bash
gh pr checks <PR_NUMBER> -R <OWNER/REPO> --watch
```

### Step 4：失敗しているチェックを列挙し、ログを取得する

```bash
gh pr checks <PR_NUMBER> -R <OWNER/REPO> --json name,bucket,link
```

`bucket` が `fail` の各チェックについて、`link` から run ID を取り出し、
失敗した部分のログのみを取得する：

```bash
gh run view <run-id> --log-failed
```

### Step 5：まずローカルで再現を試み、その結果で分類する

各失敗について、**原因を推測する前に必ずローカルでの再現を試みる**。
ログの内容だけから分類するのではなく、実際に再現するかどうかで判断する。

1. 失敗したチェック名を `.github/workflows/*.yml` 内のジョブに対応付け、失敗ログに
   表示されるステップ名・順序を手がかりに、該当ステップの `run:` コマンド（または
   `uses:` アクション）を特定する。
2. そのコマンドをローカルでそのまま実行する。
3. 結果に応じて分岐する：
   - **ローカルで再現した** → 実際のコード/ロジックのバグと判断する。修正し、
     同じコマンドを再実行してパスすることを確認してから次に進む。
   - **ローカルで再現しない**（自分の環境では成功する） → CI 環境固有の問題
     （secrets 未設定、OS/パスの違い、権限、キャッシュ、ネットワークアクセスなど）と
     判断する。ローカルで確認する手段がないため、ログの内容から直接修正する。
   - **該当ステップ・コマンドを特定できない、またはローカルで実行できない**
     （CI からしかアクセスできない外部サービスに依存するなど） → 診断不能と判断し、
     このチェックをスキップして保留リストに追加し、残りの処理を続ける。

### Step 6：グループ化してコミットする

同一の根本原因に起因する失敗（例：複数ファイルで同じ lint ルール違反）は
1つの論理的な修正としてグループ化する。グループごとに1コミットとして適用する。
各ラウンドでのユーザー承認は不要：

```bash
git add <changed files>
git commit -m "<修正内容>"
git push
```

### Step 7：全チェック成功か上限に達するまでループする

プッシュ後は Step 3 に戻り、再度チェックの完了を待つ。

- **全チェックが成功した** → Step 8 に進む。
- **プッシュ→再チェックを5ラウンド行っても全チェックが成功しない** → 停止して報告する。
- **今回のラウンドで修正可能な失敗が1件もなかった**（すべて診断不能だった） →
  それ以上ループしても進展しないため早期に停止する。

### Step 8：結果を報告する

以下を1行ずつ列挙する：

- 適用した修正：コミットハッシュ、チェック名、修正内容
- スキップしたチェック：チェック名とその理由（診断不能、flaky、外部サービスなど）

## 備考

- 失敗を通すためだけの抑制（テストの無効化、lint-ignore コメント、ステップのスキップなど）は
  行わない。根本原因を修正すること。本当に抑制が妥当と思われる場合は、実行せずに
  ユーザーに確認する。
- `gh` CLI（`gh auth login`）が必要。
