# GitHub Issue の解決

GitHub Issue のライフサイクル全体をオーケストレーションする：明確化 → 計画 → 実装 → レビュー → マージ。
各ステップは専用スキルに委譲し、このスキルは順序と判断ポイントを定義する。

## ワークフロー

### 1. Issue をブラッシュアップする

1. まず自分自身で Issue を取得する（`gh issue view <number> --json number,title,body,labels,assignees,comments`）。これにより以下の照合チェック用の独立したコンテキストを持つ。`issue-refiner` エージェントを（フォアグラウンド、`run_in_background: false`）Issue 番号または URL で起動し、このワークフローの他のステップより高い推論努力でインタビューを実行させる。サブエージェントの起動はコンテキストの壁であり、コールドスタートで最終レポートしかメインスレッドに戻らないため、インタビューの各ターンを中継する。ただし例外が1つある：

   エージェントの質問に提案されたデフォルト案が含まれる場合（`refining-github-issue` のステップ3にある「妥当なデフォルトがあれば提案する」運用による）、エージェントの提案を読む前に、自分自身で Issue を読んで独立に推定回答を作る。その上で比較する：

   - **自分の推定とエージェントのデフォルト案が一致** — 自明と判断する。ユーザーには確認せず、自分自身でそのデフォルトを `SendMessage` でエージェントに確認済みとして送り返し、自動確認した内容を記録しておく。
   - **推定が食い違う、またはデフォルト案がない** — 従来通り質問をそのままユーザーに転送し、ユーザーの回答を `SendMessage` で同じエージェントに送り返す。

   これをエージェントが Issue の更新を終えるまで繰り返す。ユーザーやエージェントに届く内容を言い換えたり要約で省略したりしない。エージェントのステップ4の確認（Issue への書き込み）の前に、自動確認済みのデフォルト一覧を diff と併せてユーザーに提示し、書き込み前に上書きする機会を残す。
2. `issue-reviewer` エージェントを（フォアグラウンド）Issue 番号または URL のみで起動する — ステップ1の議論内容は要約して渡さない。ステップ1の各ターンを自分で中継した以上、自分自身で読み直しても本当の意味でのフレッシュな目にはならない。事前情報ゼロのコールドなサブエージェントであって初めてそれが成立する。なければそのまま進む。

   指摘された曖昧点それぞれについて、サブエージェントの推定を見る前に、自分自身で Issue を読んで独立に推定回答を作る。その上で比較する：

   - **自分の推定とサブエージェントの推定が一致** — 独立した2つの読みが同じ解釈に収束したということなので、自明と判断する。その解釈を明示する形で Issue を更新し（ユーザーではなく独立した合意により解決したことを明記）、ユーザーには確認しない。
   - **推定が食い違う、またはどちらかが推定不可** — 本当に曖昧なので、ユーザーに直接確認して Issue を更新する。

コードを書く前に意図・スコープ・受け入れ条件を明確にする。

### 2. 分解するか判断する

`decomposing-github-issue` を呼び出す。
単一 PR で十分なサイズなら分解をスキップして次へ進む。
分解が必要なら、各子 Issue についてステップ 3 以降を独立して実施する。

### 3. ブランチを作成する

Issue 番号とタイトルで `creating-branch` を呼び出す。
スキルが命名規則を自動検出し、デフォルトブランチを最新化してからブランチを作成する。

### 4. 実装する

受け入れ条件に従って作業する。実装方法はプロジェクトによる：
テスト実行、設定変更、コード編集 -- Issue が求めるものを行う。
プロジェクト固有の実装関連スキル（例：DB スキーマ変更や API 仕様変更用のスキル）があれば確認し、必要に応じて使用する。

### 5. レビューする

論理的なまとまりの作業が完了したら、コミット前に `review-and-fix` をデフォルト（未コミット）モードで呼び出して問題を検出・修正する。

### 6. コミットする

`committing-changes` を呼び出す。
全ての受け入れ条件を満たすまでステップ 4〜6 を繰り返す。

### 7. 最終自己レビューする

`review-and-fix` をブランチモード（ベースブランチとの差分）で呼び出す。ステップ 4〜6 で実装は既に段階的にコミット済みのため、デフォルトモードがレビューする未コミットの差分が残っていない。問題が見つかれば修正するが、コミットは行わず修正をワーキングツリーに残す。

### 8. 修正をコミットする

`review-and-fix` が行った変更を `committing-changes` でコミットする。ステップ 7 で修正がなければこのステップは省略する。

### 9. PR を作成する

`creating-pull-request` を呼び出す。

### 10. レビューに対応する

`responding-to-pr-review` を呼び出し、PR が承認されるまで繰り返す。

### 11. retrospective を実行する

PR が `APPROVED` になったら、`retrospective` スキルを呼び出す。

1. 未コミットのファイル変更が残っていれば、`committing-changes` を
   呼び出してコミット・プッシュする。
2. レビュー承認状況を再確認する：

   ```bash
   gh pr view <PR_NUMBER> -R <OWNER/REPO> --json reviewDecision --jq .reviewDecision
   ```

   `APPROVED` でなくなっていた場合（リポジトリの設定によってはプッシュが
   承認を失効させる）、新しいレビュー活動が発生したものとして扱い、
   ステップ 10 に戻る。それ以外はステップ 12 に進む。
3. `retrospective` が何も変更しなかった場合は、そのままステップ 12 に進む。

### 12. PR を仕上げる

`finishing-pull-request` を呼び出し、PR のマージとトピックブランチの
クリーンアップを行う。

## サブスキル一覧

| ステップ | スキル |
| -------- | ------ |
| 1 | `issue-refiner`（エージェント）→ `issue-reviewer`（エージェント） |
| 2 | `decomposing-github-issue` |
| 3 | `creating-branch` |
| 5 | `review-and-fix` |
| 6 | `committing-changes` |
| 7 | `review-and-fix` |
| 8 | `committing-changes` |
| 9 | `creating-pull-request` |
| 10 | `responding-to-pr-review` |
| 11 | `retrospective` |
| 12 | `finishing-pull-request` |

## 注意事項

- ステップ 1 を完了してからコードを書く -- 受け入れ条件が不明なまま実装すると手戻りが発生する。
- ステップ 2 は小さい Issue でも必ず呼び出す。分解が必要かどうかはスキルが判断する。
- ステップ 4〜6 はステップ 7 に進む前に複数回繰り返すことがある。
- PR レビューでスコープ拡大や新たな要件が発覚した場合はステップ 1 に戻る。
- このスキルを実行してほしいというユーザーの依頼自体が、ブランチ・コミットの
  push や PR の作成を含むライフサイクル全体への事前承認である。各ステップの
  移行時に自分の判断で追加の確認を挟まないこと。止まってよいのは各サブスキルが
  既に定義している確認ポイント（分解案の承認、コミットメッセージ、PRレビューの
  対応プラン、マージ確認など）のみであり、それに上乗せしない。
