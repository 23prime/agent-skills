# イシュー駆動開発

GitHub Issue のライフサイクル全体をオーケストレーションする：明確化 → 計画 → 実装 → レビュー → マージ。
各ステップは専用スキルに委譲し、このスキルは順序と判断ポイントを定義する。

## ワークフロー

### 1. Issue をブラッシュアップする

`refining-github-issue` を Issue 番号または URL で呼び出す。
コードを書く前に意図・スコープ・受け入れ条件を明確にする。

### 2. 実装計画を立てる

`planning-github-issue` を Issue 番号または URL で呼び出す。
技術的アプローチ、サブIssueへの分割要否、分割しない場合のコミット単位での分解を決め、計画を
Issue に書き戻す。分解された場合は、各子 Issue についてこのステップから独立して実施する。

### 3. ブランチを作成する

Issue 番号とタイトルで `creating-branch` を呼び出す。
スキルが命名規則を自動検出し、デフォルトブランチを最新化してからブランチを作成する。

### 4. 実装する

ステップ2の計画にある対象のまとまりについて、受け入れ条件に従って作業する。実装方法は
プロジェクトによる：テスト実行、設定変更、コード編集 -- Issue が求めるものを行う。
プロジェクト固有の実装関連スキル（例：DB スキーマ変更や API 仕様変更用のスキル）があれば確認し、必要に応じて使用する。

### 5. レビューする

論理的なまとまりの作業が完了したら、コミット前に `review-and-fix` を未コミット範囲で呼び出して問題を検出・修正する。ステップ 2 で複数のまとまりに分割することを決めた場合は軽量モードで呼び出す（横断的な観点はステップ 7 の最終フルレビューでカバーする）。分割しなかった場合はフルモードで呼び出す（後で最終フルレビューを行う予定がないため）。

### 6. コミットする

`committing-changes` を呼び出す。
全ての受け入れ条件を満たすまでステップ 4〜6 を繰り返す。

### 7. 最終自己レビューする

`review-and-fix` をフルモード・ブランチモード（ベースブランチとの差分）で呼び出す。ステップ 4〜6 で実装は既に段階的にコミット済みのため、デフォルト範囲がレビューする未コミットの差分が残っていない。問題が見つかれば修正するが、コミットは行わず修正をワーキングツリーに残す。

このステップを省略できるのは、ブランチの差分がステップ 5 でフルモードで既にレビューした内容と一致する場合のみ — つまり、ステップ 4〜6 が1回だけ実行され、ステップ 5 がフルモードで呼ばれ（ステップ 2 で分割しなかった）、そのレビュー直後に単一のコミットが行われ、それ以降編集がない場合である。再実行すると同じ diff を二度レビューすることになる。省略した理由を説明し、（例えば `git diff main...HEAD --stat` をレビュー済みの内容と比較するなどして）同一性を断定ではなく確認すること。ステップ 5 が軽量モードで実行された場合は絶対に省略しない — 観点 4〜6 と CodeRabbit がその diff に対してまだ実行されていないため。

### 8. 修正をコミットする

`review-and-fix` が行った変更を `committing-changes` でコミットする。ステップ 7 で修正がなければこのステップは省略する。

### 9. PR を作成する

`creating-pull-request` を呼び出す。

### 10. レビューに対応する

`responding-to-pr-review` を呼び出し、PR が承認されるまで繰り返す。

### 11. retrospective を実行する

PR が `APPROVED` になったら、`retrospective` スキルを呼び出す。

1. 未コミットのファイル変更が残っていれば、`committing-changes` を
   呼び出してコミット・プッシュする。
2. レビュー承認状況を再確認する：

   ```bash
   gh pr view <PR_NUMBER> -R <OWNER/REPO> --json reviewDecision --jq .reviewDecision
   ```

   `APPROVED` でなくなっていた場合（リポジトリの設定によってはプッシュが
   承認を失効させる）、新しいレビュー活動が発生したものとして扱い、
   ステップ 10 に戻る。それ以外はステップ 12 に進む。
3. `retrospective` が何も変更しなかった場合は、そのままステップ 12 に進む。

### 12. PR を仕上げる

`finishing-pull-request` を呼び出し、PR のマージとトピックブランチの
クリーンアップを行う。

## サブスキル一覧

| ステップ | スキル |
| -------- | ------ |
| 1 | `refining-github-issue` |
| 2 | `planning-github-issue` |
| 3 | `creating-branch` |
| 5 | `review-and-fix`（分割時は軽量モード、それ以外はフルモード） |
| 6 | `committing-changes` |
| 7 | `review-and-fix`（フルモード） |
| 8 | `committing-changes` |
| 9 | `creating-pull-request` |
| 10 | `responding-to-pr-review` |
| 11 | `retrospective` |
| 12 | `finishing-pull-request` |

## 注意事項

- ステップ 1 を完了してからコードを書く -- 受け入れ条件が不明なまま実装すると手戻りが発生する。
- ステップ 2 は小さい Issue でも必ず呼び出す。分解が必要かどうかはスキルが判断する。
- ステップ 4〜6 はステップ 7 に進む前に複数回繰り返すことがある。ステップ 2 で複数の論理的な
  まとまりに分割することを決めた場合は、計画した順序でまとまりごとにステップ 4〜6 を1回ずつ
  実施し、まとまりごとに1コミットを作る。
- PR レビューでスコープ拡大や新たな要件が発覚した場合はステップ 1 に戻る。
- このスキルを実行してほしいというユーザーの依頼自体が、ブランチ・コミットの
  push や PR の作成を含むライフサイクル全体への事前承認である。各ステップの
  移行時に自分の判断で追加の確認を挟まないこと。止まってよいのは各サブスキルが
  既に定義している確認ポイント（分解案の承認、コミットメッセージ、PRレビューの
  対応プラン、マージ確認など）のみであり、それに上乗せしない。
