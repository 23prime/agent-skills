# GitHub Issue の計画

ブラッシュアップ済みの GitHub Issue を具体的な技術計画に落とし込む。まずアプローチを決め、その上で
Issue が単一 PR に収まらないほど大きい場合はサブ Issue に分割し、収まる場合はコミット単位に分解する。
結果を Issue に書き戻し、実装とレビューを通じて参照できる形で残す。

## ワークフロー

### 1. Issue を取得する

```bash
gh issue view <number> --json number,title,body,labels,assignees,comments
```

リポジトリが明示されていない場合は、カレントディレクトリの remote origin を使う。
Issue が既にブラッシュアップ済み（目的・スコープ・受け入れ条件が明確）であることを前提とする。
そうでない場合は先に `refining-github-issue` を実行する。

### 2. コードベースの文脈を把握する

Issue が触れる範囲のコードベース -- 関連ファイル、レイヤー、既存の設計パターン、関連するテスト
-- を調査する。これにより、憶測ではなく実際に存在するものに基づいてアプローチを決められる。

### 3. 技術的アプローチを決める

何をどう変更するか -- 全体的なアプローチ、関わるファイル/レイヤー、真にトレードオフのある設計判断
-- を決める。

- 一方の選択肢が明らかに優位、リポジトリ内の既存設計・実装との一貫性から答えが決まる、確立した
  規約で決まる、といった場合は自分で判断し、一文程度の根拠を書き留める -- 質問しない。
- 質問するのは、真にトレードオフがあり自明な答えがない場合に限る。

### 4. 分解が必要か判断する

ステップ3のアプローチを踏まえ、Issue が単一 PR に収まるサイズかを判断する。以下を満たせば
分解不要である：

- 単一の関心事に収まっている（1つの機能、1つの修正、1つのコード領域）。
- 単一の PR でレビュアーが無理なく読み切れる規模に収まっている。

- **単一 PR で十分な場合**：ステップ5へ進む。
- **分解が必要な場合**（本当に大きい、または複数の独立した関心事にまたがる）：ステップ6へ進む。

### 5. コミット単位に分解する

受け入れ条件が複数の独立した論理的なまとまり（別々のコミットにするのが自然な、独立した関心事・
レイヤー・ファイル群）に分かれるか、それとも単一のまとまりかを判断する。分割する場合はまとまりの
順序を、分割しない場合はその判断を書き留める。この判断はここで一度だけ行う。以降の実装では、
判断し直さずに計画済みのまとまりを順番に実装していく。

コミット単位のビルド・静的解析・ユニットテストの正しさは、ここで個別に確認する必要はない。
プロジェクトにビルド・静的解析・ユニットテスト用の pre-commit フックが設定されていれば、この
計画を使うワークフロー側のコミット工程が全てのコミットで既にそれらを実行し、失敗時は修正して
再コミットする。そちらに任せ、重複したチェックを増やさない。

ステップ7へ進む。

### 6. サブ Issue を提案・作成する

ステップ3のアプローチをもとに、サブ Issue の一覧を提案する。各サブ Issue は以下の条件を満たす
こと：

- **独立している**：一覧内の他のサブ Issue に依存せず実装できる。
- **小さい**：単一の PR で完結できる。
- **具体的**：明確なタイトルと何を実装するかの簡潔な説明がある。

以下の形式でユーザーに提示する：

```markdown
## #<number> の分解案

1. **<タイトル>** — <1行の説明>
2. **<タイトル>** — <1行の説明>
...
```

分解案を調整するか確認する（サブ Issue の追加・削除・統合、タイトルや説明の変更）。何かを作成
する前に、明示的な承認を得る。

承認された各サブ Issue を `--parent` 付きで作成し、親 Issue と紐付ける -- CLI で Sub-issues を
紐付ける唯一の方法である：

```bash
gh issue create \
  --title "<タイトル>" \
  --body "<説明>" \
  --parent <親 Issue 番号>
```

作成した各 Issue の URL を報告する。ここではどのサブ Issue の実装にも着手しない -- 各サブ Issue
について、その固有のスコープに対して `planning-github-issue` をステップ1から独立してやり直す。
親 Issue についてはステップ7へ進む。

### 7. Issue を更新する

計画の書き戻しを提案する。現在の本文との差分として提示し、書き込む前に確認を取る：

```bash
gh issue edit <number> --body "$(cat <<'EOF'
<updated_body>
EOF
)"
```

## 出力形式

計画が固まったら、以下いずれかの形式でまとめを出力する。

単一 PR の場合（ステップ5・7）：

```markdown
## Issue #<number> 実装計画

### アプローチ
<1〜3文で、何をどう変更するか>

### 実装単位
1. <まとまりの説明>
2. <まとまりの説明>
...

### 備考
<決定した設計上のトレードオフとその根拠、制約、未解決の疑問点>
```

分解した場合（ステップ6・7）：

```markdown
## Issue #<number> 実装計画

### アプローチ
<1〜3文で、何をどう変更するか>

### 分解
- #<n> <タイトル> — <url>
- #<n> <タイトル> — <url>
...

### 備考
<決定した設計上のトレードオフとその根拠、制約、未解決の疑問点>
```

## 注意事項

- サブ Issue の作成前、および Issue の更新前には必ずユーザーの確認を取る。
- 計画が Issue に書き戻されるまでは実装に着手しない。
- 分解が必要な場合、親 Issue に対して実装単位の分解は行わない -- それは各サブ Issue 自身の
  計画に属する。
