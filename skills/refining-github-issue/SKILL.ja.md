# GitHub Issue のブラッシュアップ

指定された GitHub Issue を取得し、ユーザーとの対話を通じて内容をブラッシュアップするスキル。
実装に着手する前に Issue の意図・スコープ・受け入れ条件を明確にすることが目的。

## ワークフロー

### 1. Issue を取得する

Issue 番号または URL を受け取り、`gh` CLI で取得する。

```bash
# 番号指定
gh issue view <number> --json number,title,body,labels,assignees,comments

# URL 指定の場合はリポジトリを自動解決
gh issue view <url> --json number,title,body,labels,assignees,comments
```

リポジトリが明示されていない場合は、カレントディレクトリの remote origin を使う。

### 2. Issue を分析する

取得した Issue の本文と**コメント**を読み込み、以下の観点で不明確な点・曖昧な点を洗い出す。

- **目的**: なぜこの Issue が必要か
- **スコープ**: どこまでが対象か（何を含まないか）
- **受け入れ条件**: 完了の定義は何か
- **制約・前提**: 技術的・ビジネス的な制約はあるか
- **優先度・緊急度**: どの程度急ぎか

Issue にすでに明確な目的・スコープ・受け入れ条件が揃っている場合（例: 過去にブラッシュアップ済み）は、質問をスキップして出力形式のまとめに進む。

### 3. ユーザーに質問する

一度に多くの質問を投げないこと。最も重要な疑問点を 1〜3 つに絞って聞く。
回答を受けて、さらに深掘りが必要なら追加で質問する。

質問の例：

- 「この Issue の完了条件として、〇〇は含まれますか？」
- 「〇〇の部分は既存の△△と干渉しますが、どう扱いますか？」
- 「ユーザー向けの変更ですか、それとも内部実装のみですか？」

### 4. Issue を更新する

ブラッシュアップした内容の書き戻しを提案する。
現在の本文との差分として提示し、書き込む前に確認を取る。

```bash
gh issue edit <number> --body "$(cat <<'EOF'
<refined_body>
EOF
)"
```

## 出力形式

Q&A が完了したら、以下の形式でまとめを出力する：

```markdown
## Issue #<number> ブラッシュアップ結果

### 目的
<1〜2文>

### スコープ
- 含むもの: ...
- 含まないもの: ...

### 受け入れ条件
- [ ] ...
- [ ] ...

### 備考
<制約・前提・未解決の疑問点など>
```

## 注意事項

- Issue を更新する前に必ずユーザーの確認を取る
- ユーザーが「実装に進む」と言うまでは実装しない
- 質問は簡潔に。一問一答で深掘りする
