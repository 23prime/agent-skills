# Retrospective

1つの GitHub Issue の作業――実装開始から PR 承認まで――についての現在の会話を振り返り、そこで得られた知見をセッション終了とともに失わせず、恒久的な指示やメモリに変換する。

このスキルは会話にすでに存在する内容のみを振り返る。外部履歴（`gh api`／`gh pr-review` のレビューコメントなど）は取得しない。その文脈が重要な場合は、このセッション内ですでに表面化していることを確認する（例えば `responding-to-pr-review` は承認前に PR コメントを読み、返信済みである)。

## ワークフロー

### 1. 知見を集める

会話全体を振り返り、次の3種類それぞれについて候補となる知見を挙げる。該当がなければそのカテゴリは空でよい――件数を無理に揃えない。

1. **汎用的なレビュー指摘** — ユーザー、サブエージェント（例：`review-and-fix`）、ツール（lint/CI）がこのセッション中に挙げた指摘のうち、無関係な別タスクにも当てはまるもの。このPRのコードでしか意味を持たない指摘（例：「このローカル変数名を変える」）は除外する。
2. **守れなかったルール** — プロジェクトの `CLAUDE.md`、`AGENTS.md`、`.claude/rules/*.md`（存在すれば）を読み直し、セッション中に実際に起きたことと照合する。既存のルールに違反した、または見落とした事例を書き出す。
3. **エージェント自身のつまずき点** — セッション中にエージェント自身が遭遇した誤り、誤った前提、デバッグの遠回りなど。特に、特定スキルの手順が不明瞭・不十分・想定漏れだったことに起因するつまずきに注目する。

各候補について、「内容の一文要約」「なぜ重要か（放置した場合の具体的な悪影響）」、つまずき点については「起因となったスキル（あれば）」を書き留める。

### 2. 書き込み先を判定する

各候補の性質に基づき、書き込み先をちょうど1つ割り当てる。

| 知見の性質 | 書き込み先 |
| --- | --- |
| 常に有効なプロジェクトルール | `CLAUDE.md` / `.claude/rules/` |
| ユーザーの好み・作業スタイル・プロジェクト固有の事実（プロジェクト全体のルールではないもの） | auto-memory |
| 特定スキルの手順の不備 | 該当スキルの `SKILL.md` |

複数の書き込み先に当てはまりそうな場合は、より狭い方を選ぶ（例：あるスキルのワークフローに特有のつまずきであれば、汎用的な rules ファイルより該当スキルの `SKILL.md` を優先する）。

### 3. 承認を得る

候補リスト全体を書き込み先ごとにグループ化して一度に提示する。例：

```text
## Retrospective findings

**CLAUDE.md / .claude/rules:**
1. [内容] — [なぜ重要か]

**auto-memory:**
2. [内容] — [なぜ重要か]

**SKILL.md (review-and-fix):**
3. [内容] — [なぜ重要か]

すべて適用するか？ 調整（項目の削除・文言の修正・書き込み先の変更）があれば返信するか、そのまま承認する。
```

ユーザーの回答を待つ。要望があれば修正を反映し、変更が大きい場合のみ再確認する。文言の軽微な修正は再確認不要。

### 4. 承認された項目を適用する

承認後、残った項目を書き込み先ごとに適用する。

- **CLAUDE.md / .claude/rules の項目** — `updating-agent-rules` スキルを呼び出し、各項目の確定した指示文を渡す。このスキルは `CLAUDE.md` ではなく `AGENTS.md` がプロジェクトの実質的な正本であるケースを自動判定し、プロジェクト全体の指示であればそちらに振り分ける――ここで個別対応する必要はない。
- **auto-memory の項目** — 直接書き込む。この環境の既存の auto-memory 形式（メモリディレクトリ配下の frontmatter 付き Markdown ファイル、および `MEMORY.md` への一行の追記）に従う。その形式が定義する `type` 分類（user/feedback/project/reference）をそのまま使う。新規作成の前に、更新すべき既存のメモリファイルがないか確認する。
- **SKILL.md の項目** — `writing-skills` スキルを呼び出し、対象スキル名と修正案を渡す。

何もコミットしない。すべてのファイル変更（CLAUDE.md、AGENTS.md、`.claude/rules/*.md`、SKILL.md ファイル）はワーキングツリーに未コミットのまま残す――コミットは呼び出し元（例：`resolving-github-issue`）の責任とする。auto-memory への書き込みはリポジトリ外なのでコミット不要。

### 5. 報告する

何をどこに書いたかを、項目ごとに一行で要約する。

```text
- CLAUDE.md: <一行要約>
- auto-memory: <メモリファイル名> — <一行要約>
- skills/review-and-fix/SKILL.md: <一行要約>
```

## 注意事項

- `CLAUDE.md`、`AGENTS.md`、`.claude/rules/*.md`、他スキルの `SKILL.md` を直接編集しない――常に管轄スキル（`updating-agent-rules` または `writing-skills`）に委譲し、そのスキル自身の規約や矛盾チェックを働かせる。
- 承認は項目ごとではなく一括で行う――全リストを一度に提示して確認を取る。
- どのカテゴリにも該当がなければ、その旨を伝えて終了する。報告のために知見をでっち上げない。
