# Review and Fix

## ワークフロー

### 1. diff の収集

レビュー対象の範囲を決める。

- **未コミット（デフォルト）**：未追跡ファイルを含む、まだコミットされていないすべての変更を取得する。
  1. `git diff HEAD`：追跡ファイルのステージ済み・未ステージの変更
  2. `git ls-files --others --exclude-standard`：未追跡ファイルの一覧
  3. 各未追跡ファイルに対する `git diff --no-index /dev/null <file>` の実行による diff の生成
- **ブランチ**（PR を開く前など、ブランチ全体のレビューを明示的に求められた場合）：代わりにブランチをベースと比較する。`git diff @{upstream}...HEAD`、upstream がなければ `git diff main...HEAD` を実行する。その上に未コミットの変更もあれば、それも上記の方法で収集し、レビュー対象に含める。

すべての出力をレビュー対象として結合する。レビュー対象が空の場合、レビュー対象の変更がないことをユーザーに伝える。

### 2. diff のレビュー

まず、diff にどの観点でのレビューが必要かを判断する。デフォルトは 6 観点すべてを実行し、その失敗モードが明らかに起こり得ない場合に限り観点を除外する。

- diff が実行可能なコードに触れていない場合（Markdown やコメント、静的アセットのみの変更など）、観点 1（バグとロジックエラー）と観点 2（意図しない動作変更）を除外する。
- diff が入力処理、シークレット、認証、ネットワークアクセス、ファイルアクセス、外部プロセスのいずれにも触れるコードパスを含まない場合（ドキュメントのみ・コメントのみの変更など）、観点 3（セキュリティ上の懸念）を除外する。
- 観点 4（明らかな改善点）、観点 5（関連箇所の更新漏れ）、観点 6（設計バランス）は常に残す。いずれもコードだけでなくドキュメントや設定にも当てはまる。
- diff がコードとドキュメントの両方にまたがる場合、複数領域に触れる場合、あるいはある観点が無関係だと確信できない場合は、その観点を残す。サブエージェントを 1 体余分に起動するコストは、バグを見落とすコストよりはるかに小さい。

判断後、以下を並行して実行する。

- 残った観点ごとに 1 体のサブエージェント（Agent ツール、`general-purpose` タイプ）を並列に起動する。それぞれに収集した diff と、担当観点の指示をそのまま渡す。
  1. **バグとロジックエラー**：diff 内の off-by-one、null/undefined アクセス、比較演算子の誤り、戻り値の欠落、無限ループ、競合状態を精査する。
  2. **意図しない動作変更**：diff 内のロジックの誤削除、引数の入れ違い、デフォルト値の変更を精査する。
  3. **セキュリティ上の懸念**：diff 内のハードコードされたシークレット、インジェクション脆弱性、システム境界での入力バリデーション欠如を精査する。
  4. **明らかな改善点**：diff で導入されたデッドコード、明らかに冗長な処理を精査する。
  5. **関連箇所の更新漏れ**：diff が何を変更しているか（インターフェース、フラグ、設定キー、動作、ファイル・ディレクトリ構成）を特定し、それに依存するリポジトリ内のすべての箇所が追随して更新されているかを確認する。README などのドキュメント、GitHub Actions ワークフロー（`.github/workflows/`）、その他の CI 設定、スクリプト、他スキルやファイルからのクロスリファレンスが対象。変更前の名前・値・パスをリポジトリ全体で grep し、更新漏れがないか探す。逆方向も確認する。diff が依存関係・import・ヘルパー・設定項目の最後の利用箇所を削除した場合、それ自体（package.json や go.mod のエントリ、import 文、未使用の環境変数など）も一緒に削除されているか確認する。
  6. **設計バランス**：diff がその場しのぎの最適化に走り、周辺の設計を犠牲にしていないかを確認する。判断の前に、変更したファイルの周辺コードや、リポジトリ内の類似の既存実装(他モジュール、類似関数、同じパターンの既存実装)を読むこと。この観点は観点 1〜5 と異なり diff のテキストだけに限定されない。指摘対象は、リポジトリ内の既存パターンとの不整合、既存の共有抽象化で対応できるはずのロジックの重複(またはその逆に、単一の呼び出し元のためだけに新しい抽象化を導入すること)、局所的なケースだけ修正して同様の問題が近隣の類似コードに残ったままになる構造的な選択。

  観点 1〜4 のプロンプトには次の指示を付け加える。「スタイル、フォーマット、命名、ドキュメントについては、直接バグの原因とならない限りコメントしない。」残ったすべての観点のプロンプトには次の指示を付け加える。「発見事項をファイルごとにグループ化したリストとして返す。各項目にはファイル名と該当行の概算位置、問題の一文説明、修正が明白な場合は修正案を含める。問題が見つからなかった場合はその旨を簡潔に述べる。」
- ステップ 1 と同じ範囲になるよう CodeRabbit を実行し、サブエージェントと同じ範囲のフィードバックを取得する。未コミットモードでは `coderabbit review --agent --type uncommitted`、ブランチモードでは `coderabbit review --agent --base <base-branch>` を実行する。

### 3. 発見事項の整理

サブエージェントの発見事項と CodeRabbit の発見事項を、出典ごとではなく根本原因ごとにグループ化して一つのリストに統合する。同じ根本原因が複数の出典から異なる表現で報告されることが多いため、文字列の一致ではなくファイル・行・原因で照合する。

出典を問わず、すべての発見事項を採用前に批判的に評価する。

- 実際の diff と周辺コードに照らして検証する。発見事項を鵜呑みにしない。
- 単なるスタイルの好み、誤検知、検証に耐えない指摘は却下する。
- 観点 6 の指摘については特に、周辺の既存コードまで手を入れないと成立しない提案は却下する。このワークフローは diff をその場で修正するものであり、無関係な既存コードにまでスコープを広げない。diff 自体の範囲内で修正できる指摘のみを残す(例：新規コードが使うべきだった既存の共有パターンに合わせる、など)。
- 根拠のあるバグ、ロジックエラー、セキュリティ上の懸念、関連箇所の更新漏れ、設計バランス上の問題、正当な規約違反のみを対処すべき問題として残す。

### 4. 指摘ごとに修正

生き残った対処すべき指摘それぞれについて、ワーキングツリー上で修正を適用する。ステージングやコミットは行わない。レビュー対象の変更はもともと未コミットであり、ここでコミットしてしまうとその判断をユーザーから奪ってしまう。

### 5. 再レビュー

ステップ 2〜4（サブエージェントによるレビューと、ステップ 2 と同じ範囲での CodeRabbit の両方）を、対処すべき問題がなくなるまで繰り返す。修正によって元の diff にはなかったコードに触れることがあるため、毎回どの観点が必要かを判断し直す。サブエージェントによるレビューを再実行する際、観点 5 は今回の修正によって新たな更新漏れが生じていないかに焦点を当て、観点 6 は元の diff の設計を再度蒸し返すのではなく、今回の修正が新たな設計上の不整合を生んでいないかに焦点を当てる。

### 6. 結果の報告

行ったすべての修正をユーザーに報告する。ブランチモードの場合、修正が今回の未コミット変更だけでなく、ブランチ上の既存コミットに含まれていた行にも触れているときは、既にコミット済みのコードを再度変更していることを見落としやすいため、その旨を明示的に伝える。問題が見つからなかった場合はその旨を簡潔に述べる。冗長な表現や称賛は避け、速度とシグナルを重視する。修正はコミットせずに残し、確認の上で（例えば `committing-changes` を使って）ユーザー自身がコミットするよう促す。
